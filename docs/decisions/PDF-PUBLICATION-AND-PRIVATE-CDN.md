# PDF publication and private delivery — 29 October 2026

## Decision

Retain the approved protected page reader and one-time full-file security validation. Improve preparation with bounded parallel rendering/uploading, reuse verified immutable object versions across render retries, and allow explicit automatic publication after all pages are ready. Prepare an opt-in CloudFront delivery path for the same versioned JPEG assets. No original PDF is delivered to the student reader. This is not instantaneous student availability: the administrator can schedule publication immediately, but validation/preparation still has to complete.

## Workflow and contracts

- Uploads file options offer **Publish when ready** and **Cancel automatic publication**. Existing manual Publish remains available after preparation. Replacement requests belong to one exact version; the prior published version remains accessible until publication succeeds.
- `PUT /v1/documents/:id/publication-intent` accepts `{versionId, enabled}`. Requires owning content manager or super admin, validates mapping and locks, records an audited revision, and queues a missing READY preview repair through the existing outbox. Repeating the same intent is idempotent. Cancellation remains possible if mapping/locks later change.
- Manual and deferred publication use `document-publication.ts` as the single gate. Serializable transactions, document advisory locks and bounded conflict retries protect changes. The worker checks the requesting user's current enabled status/roles, latest version, document/folder locks, academic availability and mapping at execution. Stale, failed, quarantined, incomplete or unauthorized versions cannot publish. Recoverable infrastructure failures retry without re-rendering a complete document. Permanent policy failures pause the intent and expose a reason.
- Worker reconciliation recovers a crash between READY and deferred publication. It processes pending publication after its normal SQS poll/job; completion directly invokes the same service. Publication is not an exact latency SLA if the worker is busy.
- Worker rendering defaults to 2 batch processes and 2 concurrent uploads per batch (maximum 4 in-flight uploads); each batch has an isolated temporary directory. Stop scheduling after a failure and drain in-flight work before cleanup. All pages must successfully upload before `previewReady` is committed. There is no arbitrary page limit.
- Successful antivirus/PDF validation records time, policy ID, page count and pinned S3 object version before rendering. Only that immutable version under the same policy can reuse the result. Null/non-versioned objects, changed object IDs, missing metadata or changed policy require scanning. Legacy documents get their first recorded verification normally. Bump `PDF_VERIFICATION_POLICY` when a security policy/signature rollout requires existing evidence to be invalidated; this does not itself enqueue already-completed documents for rescanning.
- `/read` checks live student entitlements and returns optional `{delivery:{baseUrl,query,expiresAt}}` for a single rendered version. Metadata responses are not cacheable. No API token or student cookie goes to CloudFront. Current page/thumbnails share one grant renewal; expired grants reauthorize through `/read`. A changed published version requires reopening. With no CDN configuration, the existing fully authorized API page stream remains in use.

## CDN authorization tradeoff

CloudFront enforces a signed custom policy for every request, including edge-cache hits. Grants default to 60 seconds and are capped at 120 seconds. Membership/lock/revocation changes prevent new grants immediately, but an already-issued bearer grant can remain usable until its expiry. This bounded window differs from the existing API's per-page live authorization. Download/print and annotation APIs continue to enforce current authorization. Client-side watermarks remain defense in depth; this change does not claim screenshot/download prevention or cryptographically personalized page images.

## Infrastructure and deployment

`infra/terraform/preview-cdn.tf` is disabled by default. It defines a CloudFront distribution, trusted signing key group, signed S3 origin access, preview-prefix-only S3 read permission and distribution-scoped KMS decrypt permission. The original-document prefix is not granted to CloudFront. Signatures are excluded from the cache key; immutable version/page paths share edge-cache entries. Minimum edge TTL is one day to override the existing S3 `private, no-store` metadata, while response headers keep browser responses `private, no-store`. Viewer signature expiry is independent of cached object lifetime. The response policy permits GET/HEAD from the configured frontend origin without browser credentials.

Before apply, inspect existing live bucket/KMS policies and merge any required statements; the new policy resources are authoritative and must not overwrite unrepresented production grants. Review the plan against isolated staging, not the existing development state without review. This task does not apply Terraform, generate a real signing key, change IAM, deploy AWS resources or enable CDN locally.

1. Generate/manage the CloudFront RSA 2048 signing key outside the repository. Supply only its public key file to Terraform; mount the private key read-only from a secret manager into the API. Rotation must overlap trusted public keys for existing grants before retiring old keys.
2. Set `enable_preview_cdn=true` and `preview_signing_public_key_file` in reviewed staging configuration. Review S3/KMS policy merge, quotas and operational logging. Apply through the approved infrastructure workflow.
3. Configure `PREVIEW_CDN_ORIGIN`, `PREVIEW_CDN_KEY_PAIR_ID`, `PREVIEW_CDN_PRIVATE_KEY_FILE`, and optionally `PREVIEW_CDN_TTL_SECONDS`. Partial configuration fails startup. Never put key contents into source, Vite variables or Terraform state.
4. Verify unsigned requests, expired signatures, another version, another origin and original-document URLs fail; verify valid signed GET/CORS, KMS access and warm-cache behavior. Validate cancellation, replacements, revocations and publication/annotation authorization in the real student UI. Enable per the accepted revocation window.
5. Enable CDN only after those checks. To roll back, remove all three CDN configuration values together and restart the API; new reads use the original authorized stream. To immediately revoke existing grants, remove the trusted signer (operationally disruptive); deleting/invalidating cached images alone is not an access-control substitute. Keep rendered objects and migrations for rollback compatibility. Deploy migrations and regenerate Prisma before API/worker rollout; old workers must finish/stop gracefully and restart on the new code. Existing processes without a watcher do not hot-reload.

## Capacity validation required

80,000 concurrent readers is a target, not a verified capacity claim. For an illustrative workload of one 300 kB page per reader every 20 seconds, delivery is about 4,000 page requests/s and 9.6 Gbit/s before thumbnails, TLS, retries and exports. A 60-second grant means roughly 1,333 renewals/s at steady state, with larger synchronized spikes. Page annotation reads still use the API/database. Simultaneous logins, mutation/annotation traffic and personalized exports need separate capacity budgets, connection pooling and scaling tests; CDN does not solve these automatically.

Staging load gates: ramp 1k → 10k → 40k → 80k independent student sessions using distributed generators and synthetic accounts, with cold/warm caches, popular/dispersed documents, realistic dwell times, thumbnail requests, renewals, revoked users, replacements, annotation writes and recovery scenarios. Record p50/p95/p99, authorization error rates, API CPU/RSS, DB query/connection saturation, CDN hit ratio, S3/KMS request rates, egress, queue age and worker resource limits. Agree numerical SLOs before running; validate AWS quotas and budget first. No 80k run was performed locally.
